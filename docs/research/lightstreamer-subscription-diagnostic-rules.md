# Lightstreamer Subscription diagnostic-rule boundaries

Research date: 2026-08-14

Client target: official Lightstreamer Web Client 9.2.3 (representative of the accepted 9.x target)

Server concepts target: current Lightstreamer Server General Concepts, v7.4.7 or greater

Scope: first-party constraints needed by `diagnostics-impl-04`. This note proposes a stable Workbench rule catalog; it does not make the catalog normative and does not implement it.

## Executive finding

Workbench can make exact statements about a captured public-API configuration, a successfully established Subscription, or a captured server callback, but those are three different evidence boundaries. The Web Client describes a newly constructed Subscription as inactive, `subscribe()` as making it active, and `isSubscribed()` as becoming true only after server-sent subscription events. Therefore, **active does not mean server-established**. [`Subscription` lifecycle](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html), [`isActive()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#isActive), [`isSubscribed()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#isSubscribed)

The public client rejects a non-null RAW snapshot preference locally. Requested buffer size is different: its setter validates the value and lifecycle, but the documented constraint says the request is useful only for filtered MERGE or DISTINCT. RAW, COMMAND, and unfiltered buffers are always unlimited under the server model, subject to the server's robustness protection. Workbench should therefore describe a captured buffer request outside filtered MERGE/DISTINCT as **not applicable**, not claim that the client rejected it or that the server used it. [`setRequestedSnapshot()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#setRequestedSnapshot), [`setRequestedBufferSize()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#setRequestedBufferSize), [Web Client 9.2.3 setter source](https://github.com/Lightstreamer/Lightstreamer-lib-client-haxe/blob/edc07fdf39fbcb4b2f397dd8b84819039b1d9f52/src/common/com/lightstreamer/client/Subscription.hx#L191-L218), [server buffer matrix](https://lightstreamer.com/docs/ls-server/latest/General%20Concepts.pdf#page=31)

Conversely, a syntactically valid request is not proof of server acceptance. Server-side limits may reduce requested frequency, and unfiltered subscription requests can be refused. Exact refusal comes from `onSubscriptionError` or `onCommandSecondLevelSubscriptionError`; the actual applied Subscription-level limit comes from `onRealMaxFrequency`. [`setRequestedMaxFrequency()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#setRequestedMaxFrequency), [`onRealMaxFrequency()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onRealMaxFrequency), [`onSubscriptionError()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onSubscriptionError), [`onCommandSecondLevelSubscriptionError()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onCommandSecondLevelSubscriptionError)

The implementation should consequently lint a single immutable observation record captured at one runtime/Evidence boundary. It must retain a typed result for every attempted getter—`available(value)`, `unavailable(reason)`, or `not-applicable`—and must never turn a thrown, missed, or lifecycle-ineligible getter into `null` or a documented default. This is a Workbench recommendation derived from the getter lifecycle restrictions and the difference between requested and server-established state above.

## First-party facts that constrain the rules

### Snapshot and buffer behavior

- RAW has no snapshot support. MERGE snapshots contain current field state, DISTINCT snapshots contain recent update history, and COMMAND snapshots contain the shortest ADD sequence needed to reconstruct current keys. [General Concepts §§3.4.1 and 3.4.3](https://lightstreamer.com/docs/ls-server/latest/General%20Concepts.pdf#page=32)
- The Web Client accepts `null` only for a RAW snapshot preference. Positive snapshot lengths are accepted only for DISTINCT; other non-RAW modes accept `null`, `"yes"`, or `"no"`. [`setRequestedSnapshot()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#setRequestedSnapshot)
- Requested buffer size is valid only for MERGE or DISTINCT when unfiltered dispatching has not been requested. A null request delegates to the server default, documented by the client as currently `1` for MERGE and `"unlimited"` for DISTINCT; the server may impose an upper limit. [`setRequestedBufferSize()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#setRequestedBufferSize)
- In filtered MERGE, exceeding the buffer silently suppresses events through merging; its default size is 1. In filtered DISTINCT, exceeding the buffer silently suppresses events; its default size is unlimited. Unlimited buffers are still subject to a server robustness limit, and sustained inbound rate above dispatch rate can increase delay and heap use. [General Concepts §§3.3.5–3.3.11](https://lightstreamer.com/docs/ls-server/latest/General%20Concepts.pdf#page=28)

The last point supports guidance about risk, not a conclusion that a particular finite or unlimited buffer is wrong. Workbench does not observe the supplier rate, server queue occupancy, server upper limit, or application tolerance from these getters.

### COMMAND and two-level behavior

- A COMMAND schema requires `key` and `command`; every COMMAND item event must carry both. Valid commands are ADD, UPDATE, and DELETE. [General Concepts §3.2.3](https://lightstreamer.com/docs/ls-server/latest/General%20Concepts.pdf#page=24)
- For a Field List, `getFields()` exposes names directly. For a Field Schema, the symbolic schema is expanded by the Metadata Adapter, so the client does not know its names; only after successful subscription can `getKeyPosition()` and `getCommandPosition()` prove the resolved positions. [`getFields()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#getFields), [`getFieldSchema()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#getFieldSchema), [`getKeyPosition()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#getKeyPosition), [`getCommandPosition()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#getCommandPosition)
- In Web Client 9.2.3, an explicit COMMAND Field List missing `key` or `command` is rejected by the constructor or `setFields()`. A symbolic Field Schema is resolved server-side, where missing `key` and `command` are reported as subscription error codes 15 and 16 respectively. [Web Client 9.2.3 field validation source](https://github.com/Lightstreamer/Lightstreamer-lib-client-haxe/blob/edc07fdf39fbcb4b2f397dd8b84819039b1d9f52/src/common/com/lightstreamer/client/Subscription.hx#L93-L109), [`setFields()` source](https://github.com/Lightstreamer/Lightstreamer-lib-client-haxe/blob/edc07fdf39fbcb4b2f397dd8b84819039b1d9f52/src/common/com/lightstreamer/client/Subscription.hx#L161-L180), [`onSubscriptionError()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onSubscriptionError)
- Configuring second-level fields or a second-level schema makes each ADD key a literal item name for an automatic MERGE Subscription with a snapshot and the first level's requested maximum frequency. DELETE removes that implicit Subscription. The second-level Data Adapter may differ from the first-level adapter. [`setCommandSecondLevelFields()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#setCommandSecondLevelFields), [`setCommandSecondLevelFieldSchema()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#setCommandSecondLevelFieldSchema), [`setCommandSecondLevelDataAdapter()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#setCommandSecondLevelDataAdapter)
- If a first- and second-level field name conflict, name lookup selects the first-level field; the second-level field remains addressable by its combined position. A schema on either level prevents the client from knowing the complete positional/name mapping without server-expanded schema knowledge. [`ItemUpdate` two-level field rules](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/ItemUpdate.html)
- Exact second-level failures are reported with the affected key: invalid literal item name (14), bad/default Data Adapter (17), group/schema failures (21–23), disallowed item mode (24), and unfiltered refusal (26–28). [`onCommandSecondLevelSubscriptionError()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onCommandSecondLevelSubscriptionError)

The configured second-level Data Adapter name alone cannot prove that the named server adapter exists, supplies every possible key in MERGE, or supports snapshots. Those are server-side facts; Workbench may state them exactly only after a corresponding server callback or other first-party server Evidence.

### Active, established, and frequency state

- `isActive()` reflects the client-side subscribe/unsubscribe lifecycle; `isSubscribed()` reflects server-established state and returns false after disconnect, unsubscribe, or a server-sent unsubscription event. [`isActive()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#isActive), [`isSubscribed()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#isSubscribed)
- `onSubscription()` is emitted before other events for that establishment epoch and invalidates previously received data. It may recur after unsubscribe/resubscribe or automatic recovery. [`onSubscription()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onSubscription)
- A requested maximum frequency applies only to MERGE, DISTINCT, or COMMAND; for COMMAND it limits UPDATE events per key and, with two-level behavior, applies to both levels. A request can reduce but cannot raise a server-side limit. [`setRequestedMaxFrequency()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#setRequestedMaxFrequency)
- Requesting `"unfiltered"` asks the server not to filter, but the request can be refused by item/user limits (26), prefiltering (27), or license terms (28). Even RAW or accepted unfiltered dispatching may have a finite edition/license limit, which `onRealMaxFrequency` reports. [`onSubscriptionError()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onSubscriptionError), [`onRealMaxFrequency()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onRealMaxFrequency), [General Concepts §§3.3.2–3.3.4](https://lightstreamer.com/docs/ls-server/latest/General%20Concepts.pdf#page=27)
- Non-positive subscription error codes are defined by the application's Metadata Adapter, not by the client catalog. Normalize them under a generic application-refusal rule while preserving the original code/message; do not infer a built-in Lightstreamer cause. [`onSubscriptionError()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onSubscriptionError)

## Proposed stable rule catalog

Rule codes are identifiers, not display copy. For a persistent condition, deduplicate re-evaluation on `(ruleCode, Subscription identity, establishment epoch, affected key when present, original server code when present)`. For a callback occurrence, include the immutable source Evidence/observation identity so renderer refresh cannot duplicate it and two genuine callbacks cannot collapse into one. An exact rule means its **observed fact** is exact at the latched boundary; severity still communicates consequence, not certainty about the application's intent.

## Inputs and latching requirements

Capture one immutable `SubscriptionDiagnosticInput` at a committed boundary, rather than retaining the live page object. The minimum input should include Subscription identity, page/client/Session and establishment epoch, current-versus-historical status, mode, Item List/Group descriptor, Field List/Schema descriptor, Data Adapter, snapshot preference, requested buffer, requested maximum frequency, second-level Field List/Schema descriptor, second-level Data Adapter, `isActive`, `isSubscribed`, latest real-frequency observation in the epoch, and correlated first-/second-level error Evidence. All getter results need explicit availability and capture provenance.

Field and item descriptors should be discriminated unions (`list`, `schema`, `unset`, `unavailable`). Calling both mutually exclusive getters after the fact is unnecessary and risks confusing a legitimate null with an unavailable value; the API explicitly distinguishes lists from symbolic schemas. [`getFields()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#getFields), [`getFieldSchema()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#getFieldSchema), [`getCommandSecondLevelFields()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#getCommandSecondLevelFields), [`getCommandSecondLevelFieldSchema()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#getCommandSecondLevelFieldSchema)

Re-establishment needs a new epoch because `onSubscription()` invalidates previously received data and may recur during recovery. Error and real-frequency callbacks must never be joined across epochs merely because they refer to the same JavaScript Subscription instance. [`onSubscription()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onSubscription), [`onUnsubscription()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onUnsubscription)

For historical Subscriptions, evaluate only the saved latch and Evidence. Routes may inspect retained configuration/error Evidence, but must never offer live remediation or reread the current page object.

## Exact versus heuristic wording

Use these wording forms:

- **Exact configuration:** “Captured requested buffer is `unlimited`.” Do not say the server granted it; the server may impose an upper limit. [`setRequestedBufferSize()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#setRequestedBufferSize)
- **Exact establishment state:** “Client-active; not server-established at boundary 418.” Do not say “subscription failed” without error Evidence. [`isSubscribed()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#isSubscribed)
- **Exact callback:** “Server refused unfiltered dispatching (26).” Preserve the original code and safely handled server message. [`onSubscriptionError()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onSubscriptionError)
- **Heuristic:** “An unlimited MERGE buffer can accumulate delay if inbound rate stays above dispatch rate; Workbench did not observe server queue occupancy.” [General Concepts §3.3.11](https://lightstreamer.com/docs/ls-server/latest/General%20Concepts.pdf#page=31)
- **Unavailable:** “Field-name conflict check unavailable because the first-level fields use a server-expanded schema.” Do not treat a symbolic schema name as a field list. [`getFieldSchema()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/Subscription.html#getFieldSchema)

An absent lost-update callback is not proof that no filtering, conflation, or suppression occurred. The callback is specified for RAW/unfiltered loss and selected COMMAND loss cases, while filtered MERGE and DISTINCT may suppress events silently when buffers fill. [`onItemLostUpdates()`](https://sdk.lightstreamer.com/ls-web-client/9.2.3/api/SubscriptionListener.html#onItemLostUpdates), [General Concepts §§3.3.5–3.3.9](https://lightstreamer.com/docs/ls-server/latest/General%20Concepts.pdf#page=28)

## Implementation implications for `diagnostics-impl-04`

1. Keep the catalog pure: input latch in, zero or more versioned observations out. Rendering, localization, and route execution must not affect rule identity or deduplication.
2. Treat every exact server code as occurrence Evidence within an establishment epoch. Current conditions such as active-but-not-established may resolve, but their prior observations remain retained rather than being recreated by every render.
3. Never emit schema/list conflict or COMMAND-field findings when expansion is unavailable. A later server callback may supply an exact finding without rewriting the earlier boundary.
4. Keep the configured request, establishment state, negotiated result, and historical state visibly separate. `null`, unavailable, not applicable, and a documented server default are four distinct values.
5. Test locally rejected RAW snapshot and explicit COMMAND-field attempts as configuration-attempt Evidence. Test non-applicable buffer requests separately: the 9.2.3 buffer setter can retain them, but the server model does not apply them outside filtered MERGE/DISTINCT.
6. Keep `LS-SUB-NONRAW-MODE-OVERLAP` and buffer-risk rules advisory. They must never block Local Injection, Scenario execution, subscription activity, or a recovery action.
